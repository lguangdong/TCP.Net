- 提问（Q15）：`using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken); timeoutCts.CancelAfter(timeout);` 这两行，包括语法
- 答复要点：
  - **语法层**：`using var` 是 C# 8 的 using 声明（作用域到当前大括号块尾，编译器生成 try/finally），多个时逆序释放；`CreateLinkedTokenSource` 是静态工厂，在新 CTS 上向各父 token 注册回调，**链接单向**（子取消不影响父）；`CancelAfter` 非阻塞、到期自动 `Cancel()`、重复调用最后一次生效、`Timeout.InfiniteTimeSpan` 表示撤销定时器
  - **设计意图**：`CancellationToken` 是只读句柄没有 `Cancel` 能力，所以想让"外部 token + 超时"两个来源合一，必须新建 Source 链接
  - **配套范式**：`catch (OperationCanceledException) when (!cancellationToken.IsCancellationRequested)` —— 外部没取消就说明是超时，转 `TimeoutException`；外部取消了就原样抛，不能吞掉
  - **必须 Dispose 的原因**：linked CTS 在父 token 上留了一个注册项，泄漏会让长生命周期父 token 的 `_registrations` 链表持续增长；`Dispose` 不触发取消只释放定时器与注册
  - **发现一处隐患**：`RpcClient.RequestAsync` 发送阶段用原始 `cancellationToken`、等待响应用 `timeoutCts.Token`，导致发送阶段无超时保护（`Channel` 队列满时会无限等），已在文档里标注建议

- 提问（Q16）：`ReadFrameAsync` 里 stream 没数据时，是不是一直挂在 `_stream.ReadAsync`，直到数据到来
- 答复要点：**会挂起，但不占线程**。`await` 让出线程池线程，`.NET Core 3.0+` 的 `NetworkStream.ReadAsync` 走操作系统真异步 IO（Windows IOCP / Unix epoll），等待期间无任何线程守着 socket。四种唤醒路径：数据到达（n>0）、对端正常关闭（n=0）、`_cts.Cancel()`（`OperationCanceledException`）、RST/网络错误（`IOException`）。**核心风险：`ReadAsync` 没有任何超时机制**（`NetworkStream.ReadTimeout` 只对同步 `Read` 生效），对端既不发送也不关闭时（拔网线 / NAT 超时 / 进程被挂起）会无限期挂死——这正是 `HeartbeatMonitor` 存在的根本原因，也是 Q7「EOF ≠ 连接断开」的第三种情况。另说明 `_cts.Cancel()` 是唯一能踢出挂起读的手段，故 `Shutdown` 里必须先 Cancel 再 `Shutdown(Both)`；半帧时被取消抛 `OperationCanceledException` 而非 `EndOfStreamException`，使 `error` 保持 null 走正常关闭分支

- 提问（Q17）：`Channel<byte[]> _sendQueue` 和 `TaskCompletionSource _closed` 这两个字段
- 答复要点：
  - **`Channel<byte[]>`**：异步生产者-消费者队列，解决"多线程并发写同一 socket 会把字节切碎"的问题（单写者硬约束）。项目配置解读：Bounded(1024) 防内存爆炸 / `FullMode.Wait` 做**反压**而非丢数据 / `SingleReader=true` 允许内部用更轻的同步原语。元素选 `byte[]` 而非 `Frame` 的关键理由——**编码在入队时完成**，相当于复制快照，避免 `Frame.Payload`（ReadOnlyMemory）指向调用方后续会被复用的缓冲区。消费用"外层 `WaitToReadAsync` + 内层 `TryRead` 批量取"，`TryComplete()` 保证把积压发完后自然退出。对比服务端 `SemaphoreSlim`：客户端要解耦"提交"和"完成"，服务端 await 到写完即可
  - **`TaskCompletionSource`**：手工完成任务。项目里一字段两用——`TrySetResult()` 的 CAS 原子性当**幂等关闭锁**（Shutdown 有读循环/写循环/Abort/Dispose 四条路径），同时 `.Task` 作为可 await 的 `Completion` 信号
  - **`RunContinuationsAsynchronously` 是重点**：不加的话 `TrySetResult()` 会**同步执行**所有续体（在调用线程上、返回前），导致死锁/栈溢出/线程饥饿/时序混乱四类问题。这是 .NET 最易漏写的选项之一
  - 语法：`new(...)` 是 C# 9 target-typed new，从字段类型推断构造

- 提问（Q18）：什么是无锁 CAS
- 答复要点：CAS = Compare-And-Swap，一条 CPU 原子指令（x86 `LOCK CMPXCHG` / ARM `LDREX`+`STREX`）完成「比较 + 条件写入」，**比较与写入之间无缝隙**；失败就自旋重试而不阻塞线程，这就是 lock-free 的本质。C# 出口是 `Interlocked.CompareExchange`，**返回值是原始值**，判断成功要写 `== comparand` 而不是 `== true`。项目内三个实例：`Interlocked.Increment(ref _seq)` 生成请求序号、`TaskCompletionSource.TrySetResult()` 的幂等跃迁、可手写 `CompareExchange(ref flag, 1, 0) == 0` 代替 `lock + bool`。三个致命限制：只能保护单个变量（多个变量要一起变就得 lock）、**ABA 问题**（需带版本号）、高竞争时自旋空转反而比 lock 慢。术语上 CAS 自旋是 lock-free 但不是 wait-free，`lock` 是 blocking

- 提问（Q19）：`new[] { _readLoop, _sendLoop }.Where(...).Select(task => task!).ToArray()` 这段
- 答复要点：目的是把两个可能为 null 的 `Task?` 字段过滤后收集成 `Task[]` 喂给 `Task.WhenAll`（`WhenAll` 不接受 null 元素会抛 `ArgumentNullException`）。语法要点：`new[] {}` 隐式类型推断成 `Task?[]`；**`Where` 只过滤值不改变泛型类型**，结果仍是 `IEnumerable<Task?>`，所以必须用 `Select(task => task!)`；`!` 是 null-forgiving operator，**纯编译期、运行时零开销**，实际为 null 照样 NRE。更优写法是 `.OfType<Task>()` 一次完成过滤 + 类型收窄，连 `!` 都不需要；或不追求 LINQ 用 `List<Task>` + `if` 判断（分配最少）。另指出 `_disposed` 是普通 `bool` 非线程安全，可改 `Interlocked.Exchange(ref _disposedFlag, 1) != 0`（呼应 Q18），但 `IAsyncDisposable` 约定不要求线程安全，加上 `Shutdown` 内部有 `TrySetResult` 兜底，现状可接受

- 提问（Q20）：既然要把发送串行化，为什么不用 `ConcurrentQueue`
- 答复要点：**`ConcurrentQueue` 只解决「多线程安全存取」，不解决「等」**。`TryDequeue` 非阻塞，队列空时消费端只能轮询，而 `Task.Delay(1)` 在 Windows 上实际约 15ms（时钟中断周期），导致「平均 7.5ms 额外延迟」或「空转烧满一核」二选一——对要测 RTT 的心跳是灾难。Channel 的 `WaitToReadAsync` 挂起 + 由信号唤醒，延迟微秒级、空闲 0 CPU。另两条派生差距：`ConcurrentQueue` 永远无界（要背压得自己配 SemaphoreSlim，且 `Count` 检查与 `Enqueue` 之间有 race）、没有 `Complete` 完成语义（要自己造标志位 + 又是轮询）。性能真相：单次入队 `ConcurrentQueue` ~20ns 快于 Channel ~50-100ns，但网络发送大部分时间队列是空的，50ns 换空闲零 CPU 很值。完整候选对比（BlockingCollection 同步阻塞占线程、BufferBlock 需额外包、手工 SemaphoreSlim 方案是劣化版 Channel）

- 提问（Q21）：.NET 各种集合形态什么时候用，要一份总结
- 答复要点：选型不是比性能，先问三件事（要不要下标访问 / 要不要按 key 查 / 要不要跨线程）。**最重要的洞察：并发集合要按「消费模型」分**——消费者有天然节拍主动拉取（Unity 每帧 `Pump()`）用 `ConcurrentQueue`；消费者无节拍、要求低延迟响应用 `Channel`。项目里正好各有一个正例：`MainThreadDispatcher._queue` 是 `ConcurrentQueue<Action>`（主线程每帧 Pull，不能阻塞），`ClientConnection._sendQueue` 是 `Channel<byte[]>`（后台循环挂起等）。另整理了复杂度对照表、`LinkedList` 只在「已持有节点引用」时才优于 `List`、`SortedList`（数组，多读少写）vs `SortedDictionary`（红黑树，频繁增删）的取舍、`ReadOnlyCollection` 只是包装不复制 vs `ImmutableArray` 真复制、`ConcurrentDictionary` 复合操作必须用 `GetOrAdd`/`AddOrUpdate`、8 个高频误区、完整决策树
